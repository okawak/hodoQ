## 2. 背景と目的

日々並行して発生する個人タスクを、優先度、状態、進捗、納期、メモとともに一画面で把握し、素早く更新できる軽量なデスクトップアプリケーションを作成する。

データはクラウドサービスに依存せずローカルに保持し、アプリケーションを終了・再起動しても失われないものとする。

## 3. 設計方針

1. **ローカルファースト**
   - ネットワーク接続なしで全機能を利用できる。
   - タスクデータはユーザー端末上のSQLiteデータベースに保存する。
2. **入力と更新の速さを優先**
   - タスク追加、状態変更、優先度変更を少ない操作で完了できるようにする。
   - すべての主要操作をボタン、メニュー、入力欄などのGUIから実行できるようにする。
   - キーボードショートカットは、慣れた利用者向けの補助手段として用意する。
3. **一覧性を優先**
   - 優先度、進捗、納期超過、状態を一覧上で判別できるようにする。
4. **UIと永続化を分離**
   - GPUIへの依存をUI層に限定し、将来GUIフレームワークを変更できる構造にする。
5. **段階的に完成形へ近づける**
   - Phase 1で日常利用可能な最小構成を作り、Phase 2以降で整理・可視化・保全機能を追加する。
   - 各Phaseの終了時点でデータを失わず、日常利用を継続できる状態にする。

## 5. 技術選定

### 5.1 `rusqlite`を採用する理由

1.0まで`sqlx`ではなく`rusqlite`を採用する。

| 観点 | `rusqlite` | `sqlx` |
| --- | --- | --- |
| 主用途 | SQLiteを直接扱う組み込みアプリ | 複数DB対応の非同期アプリ |
| API | 同期 | 非同期中心 |
| ランタイム | 不要 | Tokio等が必要 |
| SQLite固有機能 | 扱いやすい | 抽象化を意識する必要がある |
| バイナリ・依存関係 | 比較的小さい | 比較的大きい |
| 今回との適合度 | 高い | 将来サーバーDBへ移行する場合に有利 |

本アプリは単一ユーザー、単一端末、SQLite専用であり、MySQLやPostgreSQLへの接続を必要としない。非同期ランタイムを導入せず構成を小さくできる`rusqlite`が適している。

ただし、同期I/OをGPUIのUIスレッド上で直接実行しない。SQLite接続を専用のデータベースワーカースレッドに所有させ、UIとはメッセージで通信する。

### 5.2 主要ライブラリ候補

| 用途 | 候補 | 備考 |
| --- | --- | --- |
| GUI | `gpui` | pre-1.0のためバージョンを固定する |
| DB | `rusqlite` | `bundled`、`backup` featureを利用する |
| ID | `uuid` | UUID v4を使用する |
| 日時 | `time` | DBにはUnix時刻を保存する |
| リポジトリ探索 | 標準ライブラリ | 実行ファイルまたはカレントディレクトリからclone先を解決する |
| 旧保存先探索 | 標準ライブラリ | 旧版のOS標準保存先から初回のみデータをコピーする |
| エラー | `thiserror` | レイヤーごとのエラーを定義する |
| ログ | `tracing`、`tracing-subscriber` | 個人情報をログ出力しない |

依存ライブラリのバージョンは実装開始時に固定し、再現可能なビルドのため`Cargo.lock`を管理対象とする。

## 6. システム構成

```text
┌─────────────────────────────────────────┐
│ GPUI Presentation                       │
│ MainWindow / Sidebar / TaskList / Editor│
└───────────────────┬─────────────────────┘
                    │ Command / Event
┌───────────────────▼─────────────────────┐
│ Application                             │
│ AppState / UseCase / Validation         │
└───────────────────┬─────────────────────┘
                    │ Repository trait
┌───────────────────▼─────────────────────┐
│ Infrastructure                          │
│ DatabaseWorker / SqliteTaskRepository   │
└───────────────────┬─────────────────────┘
                    │ rusqlite
┌───────────────────▼─────────────────────┐
│ tasks.sqlite3                           │
└─────────────────────────────────────────┘
```

### 6.1 レイヤー責務

#### Presentation

- 画面描画とユーザー入力を扱う。
- `AppState`を参照して表示する。
- SQLやSQLiteの型を直接扱わない。
- DB処理の結果を受け取ってUI状態へ反映する。

#### Application

- タスク作成、更新、完了、削除などのユースケースを実行する。
- 入力値と状態遷移を検証する。
- DBレコードではなくドメイン型を扱う。

#### Domain

- `Task`、`Project`、`Tag`などのデータ型を定義する。
- 状態、優先度、進捗の制約を表現する。
- GPUI、SQLiteへ依存しない。

#### Infrastructure

- SQLiteの接続、SQL、マイグレーション、バックアップを扱う。
- DBレコードとドメイン型を相互変換する。
- SQLiteのエラーをアプリケーション用エラーに変換する。

### 6.2 起動・終了フロー

起動時は次の順序で処理する。

1. CLI引数を解析し、データディレクトリを決定する。
2. データディレクトリを作成し、単一起動ロックを取得する。
3. ログを初期化する。
4. SQLiteを開き、DBの整合性とスキーマバージョンを確認する。
5. 必要ならバックアップ後にマイグレーションする。
6. UI設定と初期表示データを読み込む。
7. ウィンドウを表示する。
8. バックグラウンドで日次バックアップとゴミ箱の期限切れ削除を実行する。

終了時は編集内容の保存、DBコマンドの完了、UI設定の保存、DB接続の終了、単一起動ロックの解放の順に処理する。

## 7. データベースワーカー

`rusqlite::Connection`はデータベース専用スレッドが所有する。

```text
UI thread
   │ DatabaseCommand
   ▼
command channel ──> DatabaseWorker ──> SQLite
   ▲                      │
   └──── DatabaseResult ──┘
```

### 7.1 方針

- UIスレッドではSQLを実行しない。
- ワーカーは原則1接続、1スレッドとし、書き込み順序を保証する。
- コマンドには要求IDを付け、結果を対応する画面操作へ返す。
- アプリ終了時は未処理コマンドを完了させてから接続を閉じる。
- DBエラー時はUI上で通知し、メモリ上だけ更新された状態を確定扱いにしない。

### 7.2 想定コマンド

```rust
enum DatabaseCommand {
    LoadInitialData,
    CreateTask(NewTask),
    UpdateTask(Task),
    UpdateTasks(BatchTaskUpdate),
    DeleteTask(TaskId),
    ReorderTasks(Vec<TaskPosition>),
    SaveProject(Project),
    DeleteProject(ProjectId),
    SaveTag(Tag),
    DeleteTag(TagId),
    SaveView(SavedView),
    DeleteView(SavedViewId),
    CreateBackup(PathBuf),
    RestoreBackup(PathBuf),
    ExportData(ExportRequest),
    PurgeExpiredTrash,
    Shutdown,
}
```

## 8. 画面設計

### 8.1 メイン画面

ナビゲーション用サイドバーと中央ワークスペースの2ペインを基本とする。タスクの新規作成時または選択時は右側に作成・編集ペインを追加し、中央のリスト、ボード、カレンダーと横に並べる。プロジェクト／タグの管理時だけ右側に管理ペインをオーバーレイ表示する。

画面上部には次の操作をまとめたツールバーを常時表示する。

- 作成画面を開く「新規タスク」主ボタン
- 検索入力欄
- リスト／ボード／カレンダー切り替え
- 絞り込み、複数選択、データ管理、取り消しなどをまとめた「その他」メニュー

アイコンだけでは意味が分かりにくい主要操作にはラベルを併記し、その他のアイコンにはツールチップを表示する。

```text
┌──────────────┬──────────────────────────┬────────────────────┐
│ ナビゲーション│ リスト／ボード／カレンダー │ タスクを作成・編集 │
│ 右端をドラッグ│                          │ タイトル / メモ     │
│ 今日         │ [高] 資料を確認 70% 今日 │ 状態 / 優先度       │
│ 今後7日     │ [中] 返信する   20% 明日 │ 進捗 / 納期         │
│ 期限超過     │                          │ プロジェクト / タグ │
│ すべて       │                          │ [保存]              │
└──────────────┴──────────────────────────┴────────────────────┘
```

### 8.2 サイドバー

- 今日
- 今後7日
- 期限超過
- すべて
- 完了
- プロジェクト一覧
- タグ一覧

期限超過件数と今日の未完了件数をバッジ表示する。

- 日常的に使うスマートビューだけを初期表示し、完了、アーカイブ、ゴミ箱などは「その他のビュー」で展開する。
- サイドバーと中央領域の境界を左右へドラッグし、180〜380pxの範囲で幅を変更する。変更後の幅は設定へ保存する。
- プロジェクトとタグの編集・削除操作は各管理ペインへ集約し、サイドバー行には常時表示しない。

### 8.3 タスク一覧

各行に次の情報を表示する。

- 完了チェック
- タイトル
- 優先度
- 状態
- 進捗バーとパーセント
- 納期
- プロジェクト
- 代表タグ

行クリックでタスクを選択し、完了チェックは一覧上から直接変更できるようにする。各行のホバー時にその他メニューを表示し、編集、複製、アーカイブ、削除をGUIから選択できるようにする。同じ操作は右クリックメニューからも実行できるようにする。

表示ルールは次のとおりとする。

- 期限超過：赤
- 当日または翌日が期限：黄
- 完了：文字を薄くし、取り消し線を表示
- 保留：専用アイコンを表示
- 優先度：色だけに依存せず、ラベルまたはアイコンも併用

### 8.4 右側編集ペイン

- タスク選択時にリスト、ボード、カレンダーの右へ表示する。
- ウインドウ幅が狭い場合は中央領域を縮め、編集ペインの右端を常にウインドウ右端へ揃える。
- タイトル、メモ、状態、優先度、進捗、納期、プロジェクト、タグ、アーカイブ、削除を最初から表示する。
- 中央表示と縦に積み重ねず、特に月カレンダーの表示高を減らさない。
- 編集は自動保存し、明示的な「変更を保存」ボタンも提供する。
- 「変更を保存」が成功した場合は編集ペインを閉じる。入力エラーまたはDB保存失敗時は閉じず、エラーを表示して編集を継続できるようにする。
- 文字入力項目は300〜500msのデバウンス後、選択項目は即時保存する。
- 保存中、保存済み、保存失敗を控えめに表示する。

### 8.5 新規タスク作成

- ツールバーの「新規タスク」ボタンで右側に作成ペインを開く。
- 補助操作として`Ctrl+N`（Windows）または`Cmd+N`（macOS）でも作成ペインを開ける。
- タイトル、メモ、状態、優先度、進捗、納期、プロジェクト、タグを最初から表示する。
- 「タスクを保存」ボタンで作成し、保存完了をステータスバーへ表示する。
- 初期状態は`todo`、初期優先度は`none`、進捗は0とする。
- 保存成功後は作成ペインを閉じる。入力エラーまたはDB保存失敗時は閉じない。

### 8.6 補助的なキーボードショートカット

ショートカットだけに存在する機能は作らない。以下の操作には、同じ機能を実行できるボタンまたはメニューを必ず用意する。

| 操作 | Windows | macOS |
| --- | --- | --- |
| 新規タスク | `Ctrl+N` | `Cmd+N` |
| 検索 | `Ctrl+F` | `Cmd+F` |
| 保存 | 自動保存 | 自動保存 |
| 選択移動 | `↑` / `↓` | `↑` / `↓` |
| 完了切替 | `Ctrl+Enter` | `Cmd+Enter` |
| 削除 | `Delete` | `Cmd+Backspace` |
| 詳細を閉じる | `Esc` | `Esc` |
| コマンドパレット | `Ctrl+K` | `Cmd+K` |
| 取り消し | `Ctrl+Z` | `Cmd+Z` |
| やり直し | `Ctrl+Shift+Z` | `Cmd+Shift+Z` |
| 全選択 | `Ctrl+A` | `Cmd+A` |

### 8.7 表示モード

#### リスト

- 既定の表示モードとする。
- 表形式ではなく、情報量を調整した仮想化リストとする。
- 状態、プロジェクト、優先度、納期でグループ化できる。

#### ボード

- 状態ごとに列を分ける。
- カードの列間移動で状態を変更する。
- 列内のドラッグ＆ドロップで手動順を変更する。
- アーカイブは専用ビューで扱い、通常のボード列には表示しない。

#### カレンダー

- 月表示とアジェンダ表示を提供する。
- 月表示は日曜始まりとする。
- 前月／翌月はツールチップ付きの左右矢印アイコンで移動し、「今月」ボタンで現在の月に戻る。年月の表示幅を固定し、月の桁数が変わっても各ボタンの位置を維持する。
- 日付のみ、日時指定の納期を同じカレンダー上へ表示する。
- 納期は1つの複合入力へ統合し、キーボードによる日付／日時入力、日付ピッカーによる日付選択、15分刻みの時刻選択を同じ欄から行えるようにする。
- 今日を強調し、土曜と日曜の見出しを区別する。
- 優先度は予定チップ左端の色とタスク情報で判別できるようにする。
- 納期未定タスクは月カレンダー下部の横並び領域に表示し、日付セルの表示幅を確保する。
- 外部カレンダーとの同期は行わない。

表示モードを変更しても検索条件、絞り込み、選択中のプロジェクトを維持する。

### 8.8 コマンドパレット

- タスク作成、ビュー移動、状態変更、優先度変更、バックアップなどの操作を検索して実行できる。
- GUI操作を置き換える必須機能ではなく、操作に慣れた利用者向けの補助機能とする。
- コマンドパレット内の全操作は、ツールバー、詳細ペイン、コンテキストメニュー、設定画面のいずれかからも実行できる。
- 項目名と補助キーワードを部分一致検索する。
- 破壊的操作はコマンドパレットから選択しても確認を省略しない。

### 8.9 複数選択と一括編集

- 一覧の選択モードと行チェックボックスから複数選択できる。
- 補助操作としてShiftによる範囲選択、Ctrl/Cmdによる個別選択も提供する。
- 状態、優先度、プロジェクト、タグ、納期、削除を一括変更できる。
- 選択中は画面上部に一括操作バーを表示する。
- 一括変更は1トランザクションで保存し、一部だけ成功する状態を作らない。

### 8.10 取り消しとやり直し

- 現在の起動セッション内で直近50件の変更を取り消し、やり直しできる。
- DB保存に成功した操作だけを履歴へ追加する。
- タスク、プロジェクト、タグの作成・編集・論理削除・並べ替えを対象とする。
- バックアップ復元、ゴミ箱の物理削除、自動削除は対象外とする。
- アプリ終了時に操作履歴は破棄する。

## 9. 機能要件

### 9.1 タスク

タスクは以下の属性を持つ。

| 属性 | 必須 | 内容 |
| --- | --- | --- |
| ID | 必須 | UUID |
| タイトル | 必須 | 1〜500文字 |
| メモ | 任意 | プレーンテキスト。1.0ではMarkdown描画しない |
| 状態 | 必須 | `todo`、`doing`、`blocked`、`done`、`archived` |
| 優先度 | 必須 | `none`、`low`、`medium`、`high` |
| 進捗 | 必須 | 0〜100の整数 |
| 納期種別 | 必須 | `none`、`date`、`datetime` |
| 納期日 | 条件付き | 日付のみの場合に`YYYY-MM-DD`で保持 |
| 納期日時 | 条件付き | 日時指定の場合にUnix時刻（ミリ秒）で保持 |
| プロジェクト | 任意 | 1件所属可能 |
| タグ | 任意 | 複数付与可能 |
| 表示順 | 必須 | 同一ビュー内の手動表示順に使用 |
| 作成日時 | 必須 | Unix時刻（ミリ秒） |
| 更新日時 | 必須 | Unix時刻（ミリ秒） |
| 完了日時 | 任意 | 完了時に設定 |

### 9.2 状態遷移

```text
todo ──> doing ──> done
 │         │        │
 └─────────┴──> blocked
                  │
                  └──> doing / todo

任意の未アーカイブ状態 ──> archived
```

- `done`へ変更すると進捗を100、完了日時を現在時刻にする。
- `done`から未完了状態へ戻すと完了日時を解除する。
- 再開時の進捗は0とし、必要に応じてユーザーが再設定する。
- `archived`は通常の一覧と検索から除外し、専用ビューでのみ表示する。

### 9.3 削除

- 誤操作対策として論理削除を採用する。
- 削除したタスクはゴミ箱に移動し、30日以内は復元可能とする。
- `deleted_at`から30日を経過したタスクは自動的に物理削除する。
- 自動削除は起動時に実行し、アプリを長時間起動する場合は24時間ごとにも実行する。
- 自動削除の対象件数が0件の場合はユーザーへ通知しない。
- 物理削除は「ゴミ箱を空にする」操作で行う。
- ゴミ箱を空にする操作は確認ダイアログを表示する。

### 9.4 検索と絞り込み

- タイトルとメモを部分一致検索する。
- 大文字・小文字は区別しない。
- 状態、優先度、納期、プロジェクト、タグを組み合わせて絞り込める。
- Phase 2までは`LIKE`検索とする。
- Phase 4で10,000件の性能目標を満たさない場合のみFTS5を導入する。

### 9.5 並べ替え

- 手動順
- 優先度順
- 納期順
- 更新日時順
- 作成日時順

手動並べ替えはスマートビューごとに異なる順序を持たせず、タスクの共通`sort_order`として管理する。

### 9.6 プロジェクト

- プロジェクトは名前、色、説明、表示順を持つ。
- 1タスクは0件または1件のプロジェクトへ所属できる。
- プロジェクト削除時、所属タスクは削除せず「プロジェクトなし」へ移動する。
- プロジェクトごとに未完了数、期限超過数、平均進捗を集計表示する。
- プロジェクトはアーカイブ可能とし、アーカイブ時も所属タスクを保持する。

### 9.7 タグ

- タグは名前と色を持つ。
- 1タスクに複数のタグを付与できる。
- タグ名は大文字・小文字を区別せず一意とする。
- タグ削除時は関連だけを解除し、タスクを削除しない。
- タグの複数指定ではAND検索とOR検索を選択できる。

### 9.8 スマートビューと保存済みビュー

組み込みスマートビューは以下とする。

- 今日
- 今後7日
- 期限超過
- 納期未定
- 進行中
- 保留
- 完了
- アーカイブ
- ゴミ箱

保存済みビューは、ユーザーが以下を組み合わせて名前を付けて保存できる。

- 表示モード
- 検索文字列
- 状態、優先度、納期範囲
- プロジェクト、タグ
- 並べ替え、グループ化

### 9.9 エクスポート

- 全タスクまたは現在の絞り込み結果をCSVへ出力できる。
- プロジェクト、タグを含む全データをJSONへ出力できる。
- CSVは表計算ソフトで読み込みやすいUTF-8 BOM付き形式を選択できる。
- JSONは人が読める形式とし、フォーマットバージョンを含める。
- 1.0ではCSV/JSONのインポートは行わず、完全復元にはSQLiteバックアップを使用する。

### 9.10 終了時の保存

- 編集中のデバウンス待ち処理がある場合、終了要求時に即時保存する。
- 保存完了前にウィンドウを閉じず、失敗時は再試行または変更破棄を選択させる。
- OSやプロセスの強制終了では、最後に確定したトランザクションまでを復元可能とする。

## 10. データモデル

```text
Project 1 ─── 0..N Task N ─── 0..N Tag
                         task_tags

SavedView ─── filter / sort / group / view kind
```

### 10.1 SQLiteスキーマ案

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE projects (
    id          TEXT PRIMARY KEY NOT NULL,
    name        TEXT NOT NULL CHECK (length(name) BETWEEN 1 AND 100),
    description TEXT NOT NULL DEFAULT '',
    color       TEXT,
    sort_order  INTEGER NOT NULL DEFAULT 0,
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL,
    archived_at INTEGER
);

CREATE TABLE tasks (
    id            TEXT PRIMARY KEY NOT NULL,
    title         TEXT NOT NULL CHECK (length(title) BETWEEN 1 AND 500),
    memo          TEXT NOT NULL DEFAULT '',
    status        TEXT NOT NULL DEFAULT 'todo'
                  CHECK (status IN ('todo', 'doing', 'blocked', 'done', 'archived')),
    priority      TEXT NOT NULL DEFAULT 'none'
                  CHECK (priority IN ('none', 'low', 'medium', 'high')),
    progress      INTEGER NOT NULL DEFAULT 0 CHECK (progress BETWEEN 0 AND 100),
    due_kind      TEXT NOT NULL DEFAULT 'none'
                  CHECK (due_kind IN ('none', 'date', 'datetime')),
    due_date      TEXT,
    due_at        INTEGER,
    project_id    TEXT REFERENCES projects(id) ON DELETE SET NULL,
    sort_order    INTEGER NOT NULL DEFAULT 0,
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL,
    completed_at  INTEGER,
    deleted_at    INTEGER,
    CHECK (
        (due_kind = 'none' AND due_date IS NULL AND due_at IS NULL) OR
        (due_kind = 'date' AND due_date IS NOT NULL AND due_at IS NULL) OR
        (due_kind = 'datetime' AND due_date IS NULL AND due_at IS NOT NULL)
    )
);

CREATE TABLE tags (
    id          TEXT PRIMARY KEY NOT NULL,
    name        TEXT NOT NULL COLLATE NOCASE UNIQUE
                CHECK (length(name) BETWEEN 1 AND 50),
    color       TEXT,
    created_at  INTEGER NOT NULL
);

CREATE TABLE task_tags (
    task_id TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    tag_id  TEXT NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
    PRIMARY KEY (task_id, tag_id)
);

CREATE TABLE saved_views (
    id          TEXT PRIMARY KEY NOT NULL,
    name        TEXT NOT NULL COLLATE NOCASE UNIQUE
                CHECK (length(name) BETWEEN 1 AND 100),
    view_kind   TEXT NOT NULL
                CHECK (view_kind IN ('list', 'board', 'calendar')),
    filter_json TEXT NOT NULL DEFAULT '{}',
    sort_json   TEXT NOT NULL DEFAULT '[]',
    group_by    TEXT,
    sort_order  INTEGER NOT NULL DEFAULT 0,
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL
);

CREATE INDEX idx_tasks_status ON tasks(status) WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_due_date ON tasks(due_date) WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_due_at ON tasks(due_at) WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_priority ON tasks(priority) WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_project_id ON tasks(project_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_updated_at ON tasks(updated_at) WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_deleted_at ON tasks(deleted_at);
CREATE INDEX idx_task_tags_tag_id ON task_tags(tag_id);
CREATE INDEX idx_projects_archived_at ON projects(archived_at);
CREATE INDEX idx_saved_views_sort_order ON saved_views(sort_order);
```

### 10.2 日時とタイムゾーン

- 納期なしは`due_kind = 'none'`とし、納期値を保存しない。
- 日付のみの納期は`due_kind = 'date'`とし、`due_date`へISO 8601形式の`YYYY-MM-DD`を保存する。特定の時刻へ暗黙変換しない。
- 日時指定の納期は`due_kind = 'datetime'`とし、入力されたローカル日時をUnix時刻のミリ秒へ変換して`due_at`へ保存する。
- 日時指定の表示時はOSの現在のローカルタイムゾーンへ変換する。
- 日時の入力単位は分までとし、秒は扱わない。
- 「今日」には、ローカル日付が今日の`due_date`と、ローカル時間へ変換した結果が今日になる`due_at`を表示する。
- 期限超過判定では、日付のみの納期はその日が終了するまで期限内として扱う。

### 10.3 マイグレーション

- SQLファイルを`migrations/`へ連番で配置する。
- `PRAGMA user_version`で適用済みバージョンを管理する。
- マイグレーションはトランザクション内で実行する。
- 起動中のアプリよりDBスキーマが新しい場合は書き込みを行わず、アップデートを案内する。
- 破壊的マイグレーション前には自動バックアップを作成する。

## 11. ファイル保存

### 11.1 保存場所

実行ファイルまたはカレントディレクトリから、`Cargo.toml`と`rust-toolchain.toml`を持つclone先のリポジトリルートを探索する。通常データはリポジトリ直下の`.hodoq/`へ保存する。

```text
Windows: <repository>\.hodoq\tasks.sqlite3
macOS:   <repository>/.hodoq/tasks.sqlite3
```

ログと設定はDBから分離する。

```text
.hodoq/
├── tasks.sqlite3
├── settings.json
├── backups/
├── exports/
└── logs/
```

`.hodoq/`は`.gitignore`へ登録し、コミットやpushの対象にしない。`target/debug`または`target/release`から直接起動した場合も、実行ファイルの親階層からリポジトリルートを解決する。通常とは異なる保存先が必要な場合は`--data-dir`を使用する。

旧版のOS標準アプリデータディレクトリにDBがあり、`.hodoq/tasks.sqlite3`がまだ存在しない場合は、起動中でないことをロックで確認してDB、設定、バックアップ、エクスポートを一度だけコピーする。旧データは自動削除しない。

### 11.2 SQLite設定

初期接続時に以下を設定する。

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = DELETE;
PRAGMA busy_timeout = 3000;
```

単一接続・単一ユーザーであるため、1.0では通常時にDB本体以外のファイルが残りにくい`DELETE`ジャーナルを採用する。並行読み書きが必要になった場合はWALモードを再検討する。

### 11.3 バックアップ

- SQLiteのオンラインバックアップAPIを使用する。
- ユーザーによる手動バックアップを提供する。
- 起動時に当日分の自動バックアップがなければ作成する。
- マイグレーション前に自動バックアップを作成する。
- 自動バックアップは直近5世代を保持する。
- 復元前に現在のDBもバックアップする。
- 復元対象へ`PRAGMA integrity_check`を実行し、正常な場合のみ置換する。

### 11.4 UI設定の保存

- タスクデータとは分離し、`settings.json`へ保存する。
- ウィンドウサイズ、ウィンドウ位置、最後に開いたビュー、並べ替え条件を保持する。
- 設定ファイルが破損している場合は初期値で起動し、タスクDBには影響を与えない。
- テーマ設定は将来のライトテーマ追加に備えて項目を用意するが、1.0では`dark`固定とする。

| 設定 | 内容 |
| --- | --- |
| `settings_version` | 設定形式のバージョン |
| `window_bounds` | ウィンドウ位置と大きさ |
| `maximized` | 最大化状態 |
| `sidebar_width` | サイドバー幅 |
| `detail_width` | プロジェクト／タグ管理ペイン幅 |
| `active_view` | 最後に開いた組み込み／保存済みビュー |
| `view_kind` | リスト、ボード、カレンダー |
| `sort` | 最後に使った並べ替え |
| `group_by` | 最後に使ったグループ化 |
| `theme` | 1.0では`dark` |

保存されたウィンドウ位置が現在のディスプレイ領域外にある場合は、プライマリディスプレイ中央へ戻す。

### 11.5 単一起動

- 同じデータディレクトリを使うHodoQは同時に1プロセスだけ起動可能とする。
- 起動時にデータディレクトリ内のロックファイルへOSレベルの排他ロックを取得する。
- ロック取得に失敗した場合は「HodoQは既に起動しています」と表示して終了する。
- 異なる`--data-dir`を指定した場合は、開発・テスト用途として別プロセスを起動できる。
- 異常終了後もOSがプロセス終了時に排他ロックを解放できる方式を使用し、ロックファイルの存在だけでは起動を拒否しない。

## 12. エラー処理

### 12.1 ユーザーへ表示するエラー

- DBを開けない
- 保存に失敗した
- ディスク容量が不足している
- DBが破損している
- バックアップまたは復元に失敗した
- 対応していない新しいDBスキーマである

### 12.2 方針

- 保存失敗を成功として表示しない。
- 再試行可能な操作には再試行ボタンを表示する。
- 致命的なDBエラー時は読み取り専用で起動できるようにする。
- SQL文、メモ本文、タスクタイトルを通常ログへ出力しない。
- パニックで終了する代わりに、可能な限りエラー画面へ遷移する。

## 13. 非機能要件

### 13.1 性能目標

- 通常環境で起動から操作可能になるまで1秒程度を目標とする。
- タスク10,000件で一覧スクロールが体感上滑らかであること。
- タスク追加と状態変更は操作後100ms以内に画面へ反映すること。
- 検索文字入力後100ms以内に候補を更新することを目標とする。
- 一覧は仮想化し、画面外の全行を常時描画しない。

### 13.2 可用性・耐久性

- 通常終了、強制終了後も確定済みデータを読み込めること。
- 書き込みはトランザクションで行うこと。
- マイグレーション失敗時は元のDBを維持すること。
- DBファイルが存在しない場合は新規作成すること。

### 13.3 クロスプラットフォーム

- ドメイン層とDB層はOS固有APIへ依存しない。
- ショートカット、保存先、ウィンドウ装飾のみOS差分として扱う。
- CIでWindows、macOSのビルドと自動テストを実行する。
- GPUI更新時は両OSで日本語入力、描画、スクロール、ウィンドウ操作を確認する。
- Windowsは開発時点の最新安定版Windows 11のみを保証対象とし、Windows 10は対象外とする。
- macOSは開発時点の最新安定版を保証対象とし、Apple Siliconのみをサポートする。Intel Macは対象外とする。

### 13.4 テーマ

- 1.0はGitHub Darkを参考にしたダークテーマを標準かつ唯一のテーマとする。
- GitHubの商標・画面をそのまま複製せず、配色とコントラストの方向性のみ参考にする。
- 色はUIコードへ直接記述せず、テーマトークンとして一元管理する。

| トークン | 初期値 | 用途 |
| --- | --- | --- |
| `background` | `#0D1117` | ウィンドウ背景 |
| `surface` | `#161B22` | サイドバー、詳細ペイン |
| `surface_hover` | `#1F2630` | ホバー、選択候補 |
| `border` | `#30363D` | 境界線 |
| `text_primary` | `#E6EDF3` | 本文 |
| `text_muted` | `#8B949E` | 補助情報 |
| `accent` | `#2F81F7` | 選択、リンク、主操作 |
| `success` | `#3FB950` | 完了 |
| `warning` | `#D29922` | 期限間近 |
| `danger` | `#F85149` | 期限超過、削除 |

- OSがライトテーマでも1.0ではダークテーマを維持する。
- 将来ライトテーマを追加できるよう、コンポーネントはテーマトークンのみ参照する。

### 13.5 アクセシビリティ

- 色だけに依存した状態表現を避ける。
- GUI上の主要操作は視認できるボタンまたはメニューから到達可能にする。
- キーボードだけで主要操作を完了できるようにする。
- フォーカス位置を視覚的に示す。
- OSの文字スケールを可能な範囲で尊重する。

### 13.6 セキュリティとプライバシー

- 外部通信を行わない。
- データベースは暗号化されないため、端末のユーザー権限とディスク暗号化を前提とする。
- SQLはプレースホルダーを使用し、文字列結合で生成しない。
- 外部から指定されたDBを復元する場合は整合性とスキーマを検証する。
- 機密メモの暗号化が必要になった場合はSQLCipher等を別途検討する。

### 14.1 Rustモジュール方針

- Rust Edition 2024を使用する。
- `mod.rs`は使用せず、親モジュールを`domain.rs`、子モジュールを`domain/task.rs`の形式で配置する。
- `lib.rs`をライブラリクレートのルートとし、`main.rs`は起動処理だけを呼び出す薄いバイナリとする。
- ルートモジュールの宣言は`lib.rs`、子モジュールの宣言は対応する親ファイルへ1回だけ記述する。
- クレート内の参照は原則として`crate::domain::task::Task`のような絶対パスを使用する。
- 公開範囲は最小化し、外部公開が不要な要素には`pub(crate)`を使用する。
- 大量のglob再公開は避け、API境界で必要な型だけを明示的に再公開する。
- 通常のモジュール解決を使い、特別な理由がない限り`#[path]`属性は使用しない。
- `Cargo.toml`では`edition = "2024"`を指定し、開発・CIで使用するRustの版と追加コンポーネントは`rust-toolchain.toml`に集約する。最低対応Rust版（MSRV）は別途保証しない。

## 15. テスト方針

### 15.1 単体テスト

- 検証対象の実装ファイル末尾に `#[cfg(test)] mod tests { ... }` として同居させる。
- テストのために公開範囲を拡大せず、非公開ロジックを直接検証する。
- タスク入力値の検証
- 状態遷移
- 完了・再開時の日時と進捗変更
- 検索条件の組み立て
- DBレコードとドメイン型の変換

### 15.2 DB統合テスト

- `tests/integration/main.rs` を入口とする外部テストクレートに配置し、製品の公開APIを利用する。領域別のファイルは子モジュールとしてまとめる。
- 一時ディレクトリ上にDBを作成して実行する。
- CRUD、論理削除、復元、タグ関連を確認する。
- プロジェクト削除時にタスクが保持されることを確認する。
- 保存済みビューの保存と再読み込みを確認する。
- 一括編集が単一トランザクションとなることを確認する。
- 30日未満のゴミ箱データを残し、30日経過分だけを削除することを確認する。
- 外部キー制約が有効であることを確認する。
- 各マイグレーションを空DBおよび旧バージョンDBへ適用する。
- バックアップから復元できることを確認する。

### 15.3 UIテスト

- 新規作成から自動保存までの操作
- 主要操作がGUIだけで完了できること
- ツールバー、行メニュー、右クリックメニュー、一括操作バーの動作
- フィルターと検索
- リスト、ボード、カレンダー間の切り替え
- 複数選択、一括編集、取り消し、やり直し
- コマンドパレット
- キーボード操作とフォーカス移動
- 保存失敗時の表示
- Windows/macOSでの日本語入力

非公開のWorkspaceや入力状態に依存するGPUIテストは、実装ファイル内の内部テストとして保持する。テスト配置だけを目的とした公開APIの追加やソースの再取り込みは行わない。GPUIで自動化できない領域は、リリースチェックリストによる手動確認を併用する。

### 15.4 ビルド・起動確認

- CIで`cargo fmt --check`、`cargo clippy --all-targets --all-features -- -D warnings`、`cargo test --all-targets --all-features`を実行する。
- 性能テストは `cargo test --release --lib --test integration --all-features performance_ -- --ignored --test-threads=1 --nocapture` で、内部テストと結合テストの両方を最適化ビルド・直列実行で検証する。
- Windows 11 x86_64とmacOS Apple Siliconで`cargo build --release`を実行する。
- Windowsでは`target\release\hodoq.exe`、macOSでは`target/release/hodoq`を直接起動できることを実機確認する。
- 新規DB、既存DB、旧スキーマDBの各状態で起動確認する。

## 16. ソースからのビルドと実行

本プロジェクトはインストーラーや完成バイナリの一般配布を前提としない。Gitリポジトリをcloneし、各端末でソースからビルドして利用する。

### 16.1 共通方針

- `rust-toolchain.toml`でRustツールチェーンを固定する。
- `Cargo.lock`をリポジトリへ含め、同じ依存バージョンを使用する。
- 初回ビルド時のみCargoが依存crateを取得するため、ネットワーク接続が必要となる。
- 実行時はネットワーク接続を必要としない。
- SQLiteは`rusqlite`の`bundled` featureで実行ファイルへリンクする。
- アイコン、SVGなどの実行時アセットは可能な限り実行ファイルへ埋め込み、カレントディレクトリに依存させない。
- `target/`はビルド生成物としてGit管理対象外とする。
- `.hodoq/`は`cargo clean`、再ビルド、`git pull`では削除されない。リポジトリ自体を削除するとデータも削除されるため、必要に応じて`.hodoq/`またはバックアップを別の場所へ退避する。

### 16.2 Windows

前提環境は以下とする。

- 最新安定版Windows 11 x86_64
- Git
- rustupのMSVCツールチェーン
- Visual Studio Build ToolsのC++デスクトップ開発ワークロード
- Windows SDK

PowerShellから以下の手順でビルド・実行する。

    git clone <repository-url>
    cd hodoq
    cargo build --release
    .\target\release\hodoq.exe

ビルドと実行を一度に行う場合は`cargo run --release`を使用する。通常利用では生成された`target\release\hodoq.exe`を直接起動する。

### 16.3 macOS

前提環境は以下とする。

- 最新安定版macOS
- Apple Silicon
- Git
- Xcode Command Line Tools
- rustup

    git clone <repository-url>
    cd hodoq
    cargo build --release
    ./target/release/hodoq

1.0では`.app`化、コード署名、Notarizationを行わず、Cargoが生成した実行ファイルを使用する。

### 16.4 開発実行

- `cargo run`はデバッグビルドで起動する。
- `cargo run --release`は日常利用向けの最適化ビルドで起動する。
- テスト用に`cargo run -- --data-dir <path>`を提供し、通常のDBと分離できるようにする。
- `--data-dir`を指定しない場合は、11.1節のリポジトリ内`.hodoq/`を使用する。

### 16.5 リリースプロファイル

`Cargo.toml`へ以下を設定し、軽量さと実行性能を両立する。

    [profile.release]
    lto = "thin"
    codegen-units = 1
    strip = "symbols"

### 16.6 ソース更新

更新時はリポジトリで以下を実行する。

    git pull --ff-only
    cargo build --release

- ビルド後は新しい実行ファイルを直接起動する。
- 初回起動時にスキーマ差分があれば、自動バックアップ後にマイグレーションする。
- DB、バックアップ、設定ファイルはリポジトリ外にあるため、`git pull`や`cargo clean`では削除されない。
- リポジトリ内に誤ってDBを置いた場合に備え、`*.sqlite3`、`*.sqlite3-journal`を`.gitignore`へ含める。
- WindowsとmacOSのデータは自動同期しない。別端末へ移す場合はバックアップと復元機能を使用する。

## 19. 決定事項

- アプリ名は`HodoQ（ホドキュー）`、アプリケーションIDは`dev.okawak.hodoq`とする。
- Rust Edition 2024を使用し、`mod.rs`を使わないモジュール構成とする。
- ローカルDBはSQLiteとする。
- RustのSQLiteライブラリは`rusqlite`とする。
- UIスレッドからSQLiteを直接操作しない。
- データベースはcloneしたリポジトリ内の`.hodoq/tasks.sqlite3`へ保存し、`.hodoq/`はGit管理対象外とする。
- SQLiteは1.0では`DELETE`ジャーナルモードを使用する。
- 1.0にクラウド同期、共同編集、外部連携を含めない。
- GPUIのWindows/macOS対応可否をPhase 0で最初に検証する。
- Windowsは最新安定版Windows 11のみを保証対象とする。
- macOSは最新安定版かつApple Siliconのみを保証対象とする。
- 納期は未定、日付のみ、日時指定の3形式を扱う。
- ゴミ箱内のタスクは削除から30日後に自動削除する。
- 1.0はGitHub Darkを参考にした固定ダークテーマとする。
- リポジトリをcloneしてソースからビルドし、生成された実行ファイルを直接起動する。
- インストーラー、コード署名、自動アップデート、完成バイナリの一般配布は1.0の対象外とする。

## 21. 名称設計

`HodoQ`は、日本語の「ほどく」と英語の`Queue`を組み合わせた名称である。複数の場所から積み上がるタスクの列を、一つずつほどいて整理するというプロダクトの目的を表す。表示名は`HodoQ`、読み方は「ホドキュー」、実行ファイル名とcrate名は`hodoq`とする。

現時点の簡易検索では同名の主要タスク管理アプリは確認できていない。ただし名称利用の法的保証ではないため、一般公開、アプリストア掲載、ドメイン取得を行う場合は、公開前に商標とストア上の重複を改めて調査する。
